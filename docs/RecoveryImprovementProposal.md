# Предложения по улучшению системы восстановления ExtensibleParser

Цель: сделать recovery **максимально гибким** и **всегда дающим возможность допарсить
файл до конца** с приемлемой скоростью — для IDE и компиляторов. Без перехода на
генерацию кода (она — следующий этап; структура предложений это учитывает).

Контекст:

- анализ Nitra — в `Nitra.md` (главный урок: глобальный поиск + ограничение
  *временем* = непредсказуемые зависания на отдельных сценариях);
- анализ Roslyn — в `Roslyn.md` (главный урок: лексер никогда не падает,
  recovery — инлайн, гарантированное дно «съесть до EOF»);
- текущее состояние — в `RecoveryMethods.md` / `RecoveryAuthorGuide.md`.

## Принципы (защита от «нитровской» судьбы)

1. **Work-bound, а не time-bound.** Число операций на точку/итерацию ограничено
   детерминированно (уже есть: `MaxRecoveryIterations`, `MaxRecoveryAttemptsPerPosition`).
   Time-budget добавляется *сверху* как деградация, а не как единственный предохранитель.
2. **Жадность по точкам, без глобального чарта.** Каждая ошибка чинится локально;
   стоимость O(#ошибок × локальная работа).
3. **Гарантированное дно.** Всегда существует кандидат, дающий прогресс
   (абсорбер до known-good точки или до EOF). `FatalError` — только при
   `Recoverable: false`.
4. **Состояние не отравляется.** Откат по `PatchLog` (уже есть). Мемоизация
   инвалидируется *точно*, а не «выбросить всё» (см. B1).
5. **Наблюдаемость.** Медленный сценарий должен быть виден в счётчиках/бенчмарках,
   а не в таймауте (см. раздел D).

## A. Гарантия «всегда до конца» (приоритет 1)

### A1. Кандидат последней инстанции S6 «гарантированный прогресс»

**Проблема.** Сейчас, если на точке E исчерпаны попытки
(`attempts.Count > MaxRecoveryAttemptsPerPosition`, Parser.Recovery.cs:311) —
`TryCandidate` возвращает `true` *без акцепта*, цикл ломается → `FatalError`.
S5 (абсорбер) работает только для `Success < EOF`. Для `Failure < EOF` грубого
кандидата нет.

Дополнительно (проверено эмпирически): S5, как и S6 ниже, требует snapshot в
точке E, а снимок существует только если было терминальное mismatch. Если разбор
закончился в E чисто, без mismatch, — кандидатов не генерируется вовсе:
грамматика `Module := Expr Expr`, вход `"12 34 56 78"` → `Success@6` +
`FatalError(6)`, `diags=0` (хвост `[6..12)` не покрыт деревом). И даже со
snapshot'ом S5/S6 здесь не сработают: инъекция в E не читается никогда, т.к.
стартовое правило фиксированной арифметичности ничего не парсит в позиции E.

**Предложение.** Добавить S6 (ранг 6, генерируется всегда при `E < EOF`,
**включая случай `snapshot == null`**): абсорбер `[E..S)`, где `S` = следующая
позиция, на которой First-совпадает *любой* known-good якорь (дешёвый First-скан
**без** спекулятивного парса) либо `EOF`.

Механика (то, что уже существует):
- если упавший элемент — `Ref` → memo-патч правила в E на
  `Result.Success(TerminalNode("Skipped", E, S, S-E, IsRecovery, IsAbsorber), S)`
  (как S2/S3);
- падение в начале итерации цикла, чьё правило = элемент цикла → абсорбер на
  уровне цикла (патч memo в E);
- иначе → `Injection.Absorb` на упавший терминал;
- если `snapshot == null` (mismatch на границе не было — кейс выше) →
  синтетический кадр start-правила: `Injection.Absorb` на первый терминал
  start-правила в E (этого и намерен комментарий S5: «синтетический кадр
  start-правила, §3.4 S5» — «упрощение 1.2» сохранило требование snapshot).

Последствия:
- единственный выход из `Recover` с `FatalError` — `Recoverable: false` регион
  (выполняется только при генерации S6 и без snapshot — см. выше);
- I4 (тайлинг без потерь) сохраняется — абсорбер это терминальный узел;
- I6 (латентность на корректном коде) не нарушается — S6 генерируется только
  при ошибке.

### A2. Бюджет по тирам, а не по кандидатам

**Проблема.** Задокументировано (RecoveryAuthorGuide.md, ограничение 4): S1
генерирует до `|FollowSet|+2 ≈ 9–12` кандидатов и выедает дефолтный бюджет 3
раньше, чем дойдут S2/S3/S6.

**Предложение.** Лимитировать **по стратегии-тиру**:
- S1 — общий под-бюджет (например, 4 вставки, самые дешёвые по cost);
- S2, S3, S6 — по отдельной попытке (или общему под-бюджету 3);
- либо «попыткой» считать тир, а не кандидата.

Параметр в `RecoveryProfile` (см. A3).

### A3. Профили использования (`RecoveryProfile`)

Один движок, разные контракты:

```csharp
public sealed record RecoveryProfile(
    Mode Mode,            // Ide | Compiler | Test
    TimeSpan TimeBudget,  // деградация при истощении (B4)
    int MaxIterations,
    int AttemptsPerTier,
    int MaxSkip,
    StrategyMask Enabled // битовая маска S0..S6
);
```

- **Ide**: большой бюджет, S6 обязателен, деградация до грубого восстановления
  вместо `FatalError`.
- **Compiler**: маленький бюджет; `FatalError` допустим (быстрый fail).
- **Test**: детерминизм + счётчики.

Это и есть «максимальная гибкость»: стратегия, бюджеты и жёсткость результата
настраиваются на парсер, а не на сборку.

## B. Скорость (избежать нитровских механизмов)

### B1. Точная hygiene — главный выигрыш (приоритет 1)

**Проблема.** `HygieneCore` (Parser.Recovery.cs:445) на **каждого** кандидата
удаляет **все** `Failure`-записи memo любой позиции:

```csharp
if (key.pos == currentStartPos && key.rule == startRule || _memo[key].ResultKind == Result.Kind.Failure)
    RemoveMemo(...);
```

На большом файле это тысячи записей (PEG-парсер копит failures всех неудачных
альтернатив на всех позициях), которые ре-парс заново выводит **на каждого
кандидата**. Это прямой аналог «отравленной мемоизации» Nitra.

**Семантика.** Инъекции живут в `(E, T)` и влияют только на совпадения в `E`;
top-down парс, начатый в `p`, читает только `[p..∞)`. Значит, устаревает только:

- `Failure` с `pos < E && MaxFailPos >= E` (попытка дотянулась до точки патча);
- запись start-правила на `currentStartPos`.

Валидно сохранять: `Failure` с `pos >= E` (не дотягивается до E) и
`Failure` с `pos < E && MaxFailPos < E` (локальное падение).

`Failure` уже хранит `MaxFailPos` (Result.cs:13) — проверка бесплатна.
Сuccess/Partial и так не трогаются (I2).

**Ожидаемый эффект.** O(|memo|) на кандидата → O(локальных падений). На файле
«одна ошибка в конце» почти все failures локальны и сохраняются; ре-парс
префикса становится чистым memo-hit'ами.

### B2. Кэш спекулятивных парсов на весь `Recover`

**Проблема.** `specCache` локален одному вызову `GenerateS2`
(RecoveryEngine.cs:136). Результат `Speculative(rule, s)` зависит **только от
входа** (позиции — индексы в неизменяемой строке; патчи в `E <= s` не влияют на
парс, начатый в `s`). Повторные кандидаты и итерации повторяют работу.

**Предложение.** Поднять кэш `(rule, pos) → (Ok, EndPos)` в поле на время
`Recover` (аналогично — `matchCache` из S3). Чистка — при изменении инъекций,
влияющих на позиции кэша (консервативно: кэш живёт до конца `Recover`;
корректность — из аргумента выше).

### B3. Дешёвые сканы S2/S3

**Проблема.** S2/S3 сканируют по символам `for (s = e; s <= maxS; s++)`, в S3 на
каждой позиции — TryMatch каждого терминатора (RecoveryEngine.cs:262, 397).
O(MaxSkip × #терминалов × стоимость DFA).

**Предложение.**
- прыжки по токенам: пропуск trivia одним `Trivia.TryMatch`, а не по символам
  (S2: позиции `s`, не являющиеся началом токена, не могут быть resync-точками);
- для `Literal`-терминаторов — прыжки `input.IndexOf(literal, s)` вместо
  попозиционного `TryMatch` (DFA оставить только для regex);
- pre-filter по первому символу (уже есть, `FirstMatchesAt`) — сохранить.

### B4. Time-budget с деградацией (анти-«200 мс Nitra»)

**Проблема/урок.** У Nitra был *только* time-budget → непредсказуемые зависания.
У CsNitra бюджета пока нет → худшая задержка не ограничена числом ошибок.

**Предложение.** `TimeBudget` из `RecoveryProfile` + **лестница деградации**
(по убыванию стоимости операций):

1. полное: S0–S6 со спекуляциями (S2) и полными сканами (S3, MaxSkip);
2. истощён бюджет: выключить S2-спекуляции (только First-скан), укоротить MaxSkip
   (напр., ×4);
3. ещё: только S1 (дешёвые) + S3-короткий + S6 (гарантированный прогресс);
4. жёсткий предел: принятие S6 и остановка — дерево полное, диагностика есть.

Худший случай IDE-задержки ограничен конструктивно; «не восстановилось»
деградирует в «восстановлено грубо», а не в `FatalError`.

### B5. Кластеризация дорогих точек

Если на точке E потрачено много попыток/времени (порог из профиля), следующие
итерации на точках в том же «грязном» регионе стартовать сразу с грубого тира
(S3/S6), пропуская S2. Ограничивает каскады на файлах с многими ошибками подряд —
управляемая версия нитровской проблемы N-ошибок в рамках жадной модели.

## C. Корректность и робастность

### C1. Аудит гарантии прогресса (I1)

После A1 задокументировать и покрыть тестами: из `Recover` с `FatalError`
возможен выход только при `Recoverable: false`. Проверить взаимодействия:
- S6 + `MaxSkip` (абсорбер не должен превышать лимит скана? — решение: S6
  игнорирует `MaxSkip`, это дно; задокументировать);
- S6 + вложенные `Recoverable: false` (абсорбер не должен «закрывать» строгий
  регион — если строгий регион не восстановлен, `FatalError` в нём, а не S6).

### C2. Определение семантики Partial после recovery

Сейчас Partial@EOF с непустой диагностикой недостижим (примечание в
RecoveryAuthorGuide.md). После A1 — проверить, что S6-абсорберы дают
`Success@EOF` (а не Partial), т.к. абсорбер — обычный `Result.Success`.

## D. Наблюдаемость и регрессионная сеть (то, чего не хватило Nitra)

### D1. Бенчмарк-корпус по сценариям

Именно то, что не удалось выявить в Nitra (wall-clock порог не позволял
локализовать). Корпус + ассерты на **время восстановления на файл**:

1. много мелких ошибок (100+);
2. одна ошибка в конце большого файла (проверка B1);
3. ошибка внутри вложенных циклов / в начале итерации (S2/S3-уровень цикла);
4. grammar с regex-терминалами (неточные follow-sets, S3-сканы);
5. амбивалентные longest-match случаи;
6. «грязный» файл (ошибки каждые N строк) — проверка B5.

### D2. Счётчики по стратегиям

Уже есть: `RecoveryPasses`, `EngineGenerateCalls`. Добавить:
- accept/rollback по каждой S (S0..S6);
- число удалений в hygiene до/после B1 (контроль эффекта);
- спекулятивные парсы: хиты/миссы кэша (B2);
- время по фазам: основной парс / генерация кандидатов / ре-парсы.

Тогда «тормозной сценарий» виден в метриках, а не в таймауте.

## E. Структурно (под будущий переход на кодогенерацию)

1. Держать `RecoveryEngine.Generate` чистым (статический, почти без
   зависимостей). При кодогенерации скомпилируется *ядро парсера*; **кандидатная
   модель, бюджеты и деградация останутся как есть** — это выигрыш архитектуры
   над Nitra (их recovery сплетён с rawTree-механикой).
2. `Injection` (терминалы) + `MemoPatch` (правила) — единственные единицы
   патча. Это «виртуальный edit-скрипт», независимый от представления парсера —
   контракт для будущих оптимизаций. Не усложнять.
3. Задокументировать свойство, что re-проход префикса дёшевый: memo-проверка в
   `ParseRule` (Parser.cs:220) срабатывает **до** `PushRuleFrame` — префикс
   перебирается без кадров и snapshot'ов. Сохранять при рефакторинге; это делает
   итерацию O(#top-level элементов), а не O(разбора префикса).
4. Не вводить глобальный чарт/fixpoint-по цен «ради оптимальности» — опыт Nitra:
   это источник и сложности отладки, и зависаний. Жадность + гарантированное дно
   — осознанный выбор.

## F. Из Roslyn (по итогам анализа, см. Roslyn.md)

Roslyn подтверждает общую форму (инъекция + пропуск + гарантированное дно +
предохранители) и даёт шесть конкретных приёмов:

### R1. Мусорный терминал (эквивалент `BadToken` лексера) — приоритет 1

**Урок.** Лексер Roslyn никогда не падает: мусор = `BadToken`
(Lexer.cs:688-732, лимит 200). У CsNitra нет «мусорного» терминала: если
в точке E *ни один* терминал не совпал, парсер получает Failure и весь
взрывной поиск S2/S3/S6.

**Предложение.** Встроенный терминал `Garbage`: TryMatch в `p` =
«ни один терминал терминального набора не совпал в `p`» (тот же цикл, что
и в TDOPP-правиле — бесплатно), потребляет до первой позиции, где *кто-то*
совпадает, или до лимита (напр., 64 символа / 16 токенов). Стоимость:
O(k × #терминалов) только на настоящем мусоре.

**Эффект.** Класс сценариев «ничего не совпало» (битые символы, чужой
синтаксис в блоке, обрезанный файл) превращается из Failure-сценария
в локальный «съел мусорный токен» — уровень S0/S1. S2/S3/S6 остаются
для структурных ошибок, а не для мусора.

### R2. Стоп-предикат из ожидаемого множества

**Урок.** `IsTerminator()` (LanguageParser.cs:94-137) останавливает skip
по *контекстному* предикату, а не по глобальному списку.

**Предложение.** S3/S6 останавливают скан на первой позиции, где совпадает
*ожидаемое продолжение*: First-множества структур, ожидаемых вышестоящим
правилом в точке E (FirstSets движок уже считает), ∪ текущих терминаторов.
Сокращает дистанцию пропуска и число ложных синхронизаций.

### R3. Stack-предохранитель (эквивалент `ParseWithStackGuard`)

**Текущее состояние (проверено).** Depth-guard уже есть: `_maxParseDepth =
inputLength * 4 + 128` (Parser.Recovery.cs:152-156, `BeginParseFrame` абортит
ветку в `Failure`), но он некалиброван: добавлен под репро 3.0a
(`StackGuardTests`, 27-символьный вход, бесконечная рекурсия) и рассчитан только
на мелкие входы. Эмпирика: `Expr := "(" Expr ")" | Digits`, 300 уровней
вложенности (601 символ) — OK, 350 уровней (701 символ) — процесс погибает
(`StackOverflowException`, exit 0xC00000FD): guard допускает ~2900 уровней парса,
а стандартный 1MB-стек кончается раньше. `catch` в ExtensibleParser нет вовсе.

**Предложение.** (1) Перекалибровать depth-guard под реальный бюджет стека;
(2) `try/catch (StackOverflowException)` (ловится с .NET Core 3.0) на входе
`Parse` → корневой узел-абсорбер на весь ввод + диагностика `InsufficientStack`.
Для справки: Roslyn делает и превентивный `StackGuard.EnsureSufficientExecutionStack`
в 5 горячих точках (LanguageParser.cs:241, 2593, 3237, 8352, 11475 — бросает
*до* реального исчерпания), и восстановление в 4 точках входа, включая mid-parse
(`ParseMemberDeclaration` → `IncompleteMember`, `ParseStatement` → `EmptyStatement`,
`ParseExpression` → missing identifier — локальный плохой узел, а не только
«весь файл одним BadToken»). Защита от патологической вложенности
(рекурсивный интерпретируемый парсер!).

### R4. Runaway-режим

**Урок.** `RecoveringFromRunawayLexing` (Lexer_StringLiteral.cs:1148):
после ошибки — дешёвый выход (следующая кавычка = закрывающая).
У CsNitra — B5 (после дорогой точки — сразу грубый тир). Совпадает,
зафиксировать как единый паттерн.

### R5. Размещение диагностики

**Урок.** Missing-токен, ожидавшийся на новой строке → нулевая диагностика
в конце предыдущей строки (SyntaxParser.cs:622-635). Для качества squiggle
в IDE перенести в CsNitra (постановка span'ов RecoveryDiagnostic).

### R6. «Дерево покрывает весь ввод» — как инвариант

**Следствие.** R1 + S6 вместе дают CsNitra свойство Roslyn: покрывающее
весь ввод дерево существует *всегда* — I4 становится структурным, а не
договорным. Инвариант достигается только если S6 генерируется и без snapshot
(хвостовой мусор без mismatch на границе — проверенный кейс, см. A1).
Зафиксировать как целевой инвариант.

**Чего не брать из Roslyn:** hand-written стоп-предикаты (CsNitra —
grammar-driven — его ценность), отказ от re-парса (невозможен при неполном
потоке терминалов), trivia-представление пропущенного (дизайн-решение).

## Приоритеты и порядок работ

| # | Что | Эффект | Оценка |
|---|---|---|---|
| 1 | A1 (S6 fallback) + A2 (бюджеты по тирам) | «всегда до конца» | средняя |
| 2 | B1 (точная hygiene) | главный выигрыш в скорости | маленькая |
| 3 | R1 (мусорный терминал) | упрощает класс Failure-сценариев | средняя |
| 4 | A3 (профили) + B4 (time-budget с деградацией) | предсказуемая латентность IDE | средняя |
| 5 | B2 (кэш спекуляций) + B3 (токен-сканы) + R2 (стоп-предикат) | скорость на больших файлах | маленькая |
| 6 | D1 (корпус) + D2 (счётчики) | защита от регрессий | маленькая |
