# Анализ восстановления ошибок в Roslyn (C#)

Источники: `C:\RSDN\LexerRecoveryStrategy.md` (21 стратегии лексера),
`C:\RSDN\ParserRecoveryStrategy.md` (39 стратегий парсера) и код
`C:\RSDN\roslyn\src\Compilers\CSharp\Portable\Parser\` — ключевые места
проверены по исходникам (указания `Файл:строка` ниже — из кода).

---

## 1. Философия (4 принципа)

1. **Лексер никогда не падает.** Поток токенов всегда покрывает весь вход:
   мусор — `BadToken` (лимит 200 шт., дальше остаток файла = один `BadToken`,
   Lexer.cs:688-732). Лексер только *сообщает*, не *прерывается*.
2. **Один проход, без ре-парса.** Парсер не возвращается назад и не
   пересобирает префикс. Recovery — *инлайн*: отсутствующий токен
   инженируется нулевой шириной (SyntaxParser.cs:521-534), плохие токены
   съедаются и прикрепляются к ближайшему узлу как trivia
   (`AddSkippedSyntax`, SyntaxParser.cs:1018-1102). Стоимость recovery =
   O(пропущенных токенов), никогда O(разбора).
3. **Стоп-предикаты из контекста.** Битовая маска `TerminatorState` (29 флагов,
   LanguageParser.cs:57-90) + `IsTerminator()` (LanguageParser.cs:94-137) —
   «где закончить пропуск» решается по текущему контексту правила, а не
   глобально.
4. **Глобальные предохранители.** `ParseWithStackGuard` (LanguageParser.cs:207-234):
   `InsufficientExecutionStackException` → весь вход = один `BadToken` + EOF.
   `IsMakingProgress` (SyntaxParser.cs:1178-1189): guardrail против бесконечных
   циклов (assert в debug). Лимит 200 BadToken'ов.

## 2. Лексер: 21 стратегия (сводка)

Ключевые по значению для CsNitra:

| # | Стратегия | Суть | Код |
|---|---|---|---|
| 1 | BadToken + лимит 200 | мусор = токен; >200 → остаток файла одним токеном | Lexer.cs:688-732 |
| 5 | Identifier backtrack | не собрал ни символа → `TextWindow.Reset(start)`, возврат `false` вызывающему | Lexer.cs:1619-1623 |
| 8 | Runaway-режим интерполяции | при ошибке в строке следующая кавычка = закрывающая (дёшевый выход) | Lexer_StringLiteral.cs:1148 |
| 13 | Инъекция фиктивного `0` | плохая экспонента `1e` → в буфер добавляется `0`, парсер получает валидное число | Lexer.cs:938-959 |
| 17 | Незакрытый комментарий | EOF внутри `/* */` → весь остаток = комментарий | Lexer.cs:2208-2233 |

Остальные (16 шт.) — точечные: суррогатные пары, `@`-последовательности,
unterminated string/char, escapes, директивы, merge-conflict-маркеры,
Razor. Общий паттерн всех: **потребить минимум (1 символ/токен) или максимум
(до EOF), зафиксировать ошибку, продолжить сканирование** — никогда не
остановиться.

## 3. Парсер: 39 стратегий = один общий механизм + контекст

Все 39 «стратегий» — это параметризованные экземпляры **двух примитивов**:

### Примитив A: инъекция отсутствующего токена

`EatToken(kind)` (SyntaxParser.cs:521-534): совпал — съесть; не совпал —
вернуть `MissingToken` (нулевая ширина, диагностика «ожидалось X, получено Y»),
реальный токен **не потребляется** — его съест skip-цикл.
Варианты: `EatTokenAsKind` (заменить + съесть), `EatTokenEvenWithIncorrectKind`
(съесть чужой токен с диагностикой, SyntaxParser.cs:609-636 — см. там же
размещение squiggle: если токен на следующей строке — нулевая диагностика в
конце предыдущей), `EatTokenWithPrejudice`, `EatContextualToken`.

### Примитив B: цикл пропуска с контекстным стопом

`SkipBadTokensWithExpectedKind` (LanguageParser.cs:4616-4641) — ядро:

```csharp
while (isNotExpectedFunction(this))
{
    if (abortFunction(this, closeKind) || this.IsTerminator())
        return PostSkipAction.Abort;   // стоп по контексту → правило сдаётся
    var token = (first && !diag) ? EatTokenEvenWithIncorrectKind(expected)
                                 : EatToken();   // ошибка только на ПЕРВОМ токене
    nodes.Add(token);
}
trailingTrivia = ...;   // пропущенное → SkippedTokensTrivia на стартовом токене
```

Правила:
- **один диагноз на цикл** — только первый плохой токен получает ошибку,
  остальные молча (подавление шума);
- `isNotExpectedFunction` / `abortFunction` — **hand-written** лямбды на каждое
  правило (11 контекстных callback'ов: `skipBadParameterListTokens`,
  `skipBadEnumMemberListTokens`, ...);
- `IsTerminator()` — 29-флаговая маска контекста.

### Специальные случаи

- `SkipBadMemberListTokens` (LanguageParser.cs:2094-2152): **всегда потребляет
  минимум один токен** (гарантия прогресса), стоп по `CanStartMember` /
  балансу скобок (`curlyCount`) / EOF.
- `ConsumeUnexpectedTokens` (LanguageParser.cs:14673-14688): **дно** — съесть
  всё до EOF, одно `ERR_UnexpectedToken`, остаток → trivia. Это Roslyn-аналог
  «гарантированного S6».
- `ParseWithStackGuard` + `CreateForGlobalFailure` (LanguageParser.cs:207-234):
  stack overflow → весь файл одним BadToken'ом, `ForceEndOfFile()`.
- `IsMakingProgress` (SyntaxParser.cs:1178-1189): guardrail для
  `while`-циклов парсера — позиция токена должна расти, иначе assert.
- 11 специализированных recovery (misplaced `else`, `for`→`foreach`,
  запятая вместо `;` в `for`, `;` как `,` в списках и т.п.) — точечные
  «умные» правки, которые hand-written правила дают лучше, чем общий механизм.

### Инфраструктура: ничего не теряется

`AddSkippedSyntax` (SyntaxParser.cs:1018-1102): пропущенное дерево
декомпозируется на токены и прикрепляется к ближайшему реальному токену как
`SkippedTokensTrivia`; первая диагностика переносится на цель (в комментарии
в коде задокументирован известный минус: переносится только *первая*
диагностика, более релевантная может потеряться).

## 4. Чего у Roslyn нет (ограничения)

1. **Контекст hand-written.** 29 флагов, 11 callback'ов, десятки лямбд
   `isNotExpectedFunction` — это ручной труд для *одного* языка. Не масштабируется
   на «грамматика как данные».
2. **Один проход работает, потому что токеновый поток полон.** Лексер гарантирует
   покрытие всего входа; парсеру никогда не нужно «перевыводить» токены.
   Для TDOPP-грамматик, где терминал может *не совпасть* (поток неполный),
   ре-вывод неизбежен — отсюда мемоизация и re-парс в CsNitra.
3. **Нет модели стоимости.** Выбор «вставить» vs «пропустить» — жёсткая
   политика, не оптимизация. Никогда не удаляет токен из дерева (токены
   неизменны; «удаление» = обёртка в trivia).
4. **Нет поиска resync-точки.** Стоп-предикаты знают, *когда остановиться*,
   но «перепрыгнуть к следующему валидному месту» — это и есть skip-цикл
   по одному токену (O(пропущенных)), а не поиск.
5. **Нет инкрементальности в recovery** — Blender (инкрементальная инвалидация)
   вынесен отдельно и к recovery отношения не имеет.

## 5. Сопоставление с CsNitra

| Roslyn | CsNitra | Комментарий |
|---|---|---|
| `EatToken(kind)` → MissingToken | S1 (Missing-инъекция) | CsNitra делает это кандидатом + re-парс; Roslyn — инлайн. Цена re-парса скомпенсирована мемо (hit-префикс дёшев). |
| `SkipBad*` + `IsTerminator` | S2/S3 (скан к resync-точке) | Roslyn: стоп-предикат из контекста, O(пропущенных). CsNitra: *поиск* точки (First-скан + спекуляция) — дороже, но grammar-driven. |
| `ConsumeUnexpectedTokens` | **отсутствует** → предложен S6 | Точно то же: дно «съесть до EOF». Валидация A1. |
| `SkipBadMemberListTokens` (≥1 токен) | I1 (e монотонно растёт) | Оба гарантируют прогресс; у Roslyn — assert, у CsNitra — runtime-брос. |
| BadToken (лексер) | **отсутствует** | У CsNitra нет «мусорного» терминала — см. R1. |
| `ParseWithStackGuard` | **отсутствует** | См. R3. |
| лимит 200 BadToken → остаток одним | `MaxRecoveryIterations` / S6 | Аналог есть после A1. |
| Runaway-режим («после ошибки — дешёвый выход») | **отсутствует** | См. B5. |
| trivia для пропущенного | абсорбер — узел дерева | Дизайн-разница: у Roslyn пропущенное остаётся *токенами* (trivia) — удобнее для IDE-запросов по токенам. У CsNitra абсорбер — синтетический терминальный узел с текстом. |
| одна диагностика на skip-цикл | абсорбер = одна диагностика | Совпадает. |

## 6. Что взять в CsNitra (детали — в RecoveryImprovementProposal.md, раздел F)

1. **R1. Мусорный терминал (эквивалент BadToken).** Терминал, который
   «совпадает», когда *ни один* терминал не совпадает, и потребляет до
   следующей позиции, где кто-то совпадает (или до лимита). Превращает
   Failure-сценарии «ничего не совпало» в локальный «съел мусор» —
   самый сильный структурный урок лексера Roslyn.
2. **R2. Стоп-предикат из ожидаемого множества.** S3/S6 должны останавливать
   скан на позиции, где совпадает *ожидаемое продолжение* (First-множества
   вышестоящего правила в точке E), а не только глобальные якоря/терминаторы.
   FirstSets в движке уже считаются.
3. **R3. Stack-предохранитель.** `try/catch (StackOverflowException)`
   (ловится с .NET Core 3.0) на входе `Parse` → корневой узел с абсорбером
   на весь ввод + диагностика. Эквивалент `ParseWithStackGuard`.
4. **R4. Runaway-режим.** После первой ошибки в «грязном» регионе —
   дешёвые выходы (аналог `RecoveringFromRunawayLexing`): уже учтено в B5.
5. **R5. Размещение диагностики.** Missing-токен на новой строке → нулевая
   диагностика в конце предыдущей (SyntaxParser.cs:622-635) — для качества
   squiggle в IDE.
6. **R6. «Лексер никогда не падает» как инвариант.** R1 + S6 вместе дают
   CsNitra свойство Roslyn: *дерево, покрывающее весь вход, существует всегда* —
   I4 становится структурным, а не только договорным.

Чего **не** брать: hand-written стоп-предикаты (CsNitra — grammar-driven,
это его ценность), отказ от re-парса (невозможен при неполном потоке терминалов),
trivia-представление пропущенного (дизайн-решение, не обязательно).
