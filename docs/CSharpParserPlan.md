# Дорожная карта: парсер C# 1–14 на CsNitra

## Подход

- Грамматика = текстовые файлы CsNitra, по одному файлу на версию C#: `Cs1.grammar`, `Cs2.grammar`, …, `Cs14.grammar`.
- Грамматика C# 14 = слияние файлов 1→14 по возрастанию; каждая новая версия расширяет предыдущие: новые правила + новые альтернативы существующих правил (в т.ч. TDOPP-правил вроде `Expression`).
- Источник «реальной» грамматики: Roslyn (`C:\RSDN\roslyn\`) — `src/Compilers/CSharp/Syntax/` (`SyntaxParser.cs` — основной парсер, `TokenList.cs` — таблица токенов), тесты `tests/Compilers/CSharp/`. Версионность в Roslyn задана проверками `CSharpVersion` — по ним и разбиваем на версии.
- Сначала текст грамматики парсится в рантайме (`CsNitraParser` + `BuildFromAst` — путь уже работает, покрыт тестами). Перенос сборки грамматики в Roslyn source generator (текст → `Rule` на этапе компиляции) — завершающая итерация.
- Язык текстовой грамматики расширяем только когда версии это потребует; расширение метациркулярно: `CsNitraParser` + AST + visitor + `RuleGenerator` + TypeChecker + тесты (паттерн `ShouldParseItself`).
- Размер задачи = одна сессия субагента. Исследование кодовых баз — только через субагента с roslyn MCP.
- **Декларативность прежде всего** (решение пользователя): правила описываются декларативно текстом грамматики; ручные матчеры (hand-written `Terminal`) — только там, где разбор невозможно или слишком сложно выразить декларативными конструкциями. Все литералы стремятся сделать декларативными (Этап 6).
- **Гранулярность задач** (урок T1.4): одна сессия субагента не должна уходить в предел контекста (T1.4 отработал 237K/256K — на грани сжатия). Широкие пункты декомпозируются на мелкие подпункты (по конструкции/типу), каждый — отдельная короткая сессия субагента.

## Строковые литералы: архитектура (решение, сентябрь 2026)

Программная (hand-written-сканерная) реализация **интерполированных** строк отклонена: внутри
интерполяции могут быть сложные выражения, сами содержащие интерполяции/лямбды с `{ }` —
баланс скобок на уровне сканера некорректен. Интерполированные строки (все с `$`) строятся
**грамматикой** (основной парсер, рекурсия): дыра = `{ Expression }`, где `Expression` — реальное
правило выражений. Примерный шаблон (старый dialekt Nitra): `C:\RSDN\nitra\Grammars\CSharp\CSharp.Grammar\CSharp\CS6\CS6Literals.nitra`.

- **Не-интерполированные** строки (обычные, verbatim, raw без `$`) — остаются hand-written
  терминалами (рекурсии нет, DFA/сканер корректны). Уже реализовано: `StringLiteralScanner`.
- **Интерполированные** — грамматические правила. Пока — 3 явных варианта по числу `$`:
  один `$` (дыры в `{ }`), два `$$` (дыры в `{{ }}`), три `$$$` (дыры в `{{{ }}}`). Общее
  (произвольное число `$`) требует передачи контекста — см. отдельный пункт ниже.
- Дыра в raw-интерполированной строке с `N` знаками `$` открывается/закрывается `N` фигурными
  скобками; одиночные/недвойные скобки — обычный текст. Количество `$` **контекстно замкнуто**
  на количество скобок — выразить в текущем парсере нельзя, поэтому 3 варианта расписаны явно.

## Этап 5 — Дообработка парсера: передача контекста (отдельный пункт)

Цель: позволить грамматике вычислять/прокидывать контекст, чтобы не расписывать варианты в лоб.
Целевая форма (пример из обсуждения):

```
// token гарантирует единый лексический узел
token Dollars = '$'+;

// маркеры, принимающие вычисленное число скобок
token Open(int localCount)  = '{'{localCount} !'{';
token Close(int localCount) = '}'{localCount} !'}';

// Идеальный быстрый ДКА-токен для сырых строк.
// Спотыкается только на кавычках (конец строки) и скобках (интерполяция).
token BaseText = [^"{}]+; 

syntax Content(int localCount)
  = Open(localCount) Expression Close(localCount) 
  | BaseText                                      // Летит по тексту на максимальной скорости ДКА
  | '{'                                           
  | '}'                                           
  | !'"""' '"'                                    // Безопасно обрабатывает одиночные/двойные кавычки
  ;

syntax RawInterpolatedString
  = Dollars '"""' Content(Count(Dollars))* '"""';
```

Что нужно от парсера/мета-грамматики:
- параметризуемые правила (`syntax Content(int localCount)`),
- вычисление значения по узлу (`Count(Dollars)` — длина промаatched-ранки `$`),
- повторение с вычисленным счётчиком (`'{'{localCount}`),
- lookahead `!'{` уже есть (`!`-предикат) — проверить совместимость с параметрами.

Результат: единое общее правило `RawInterpolatedString` вместо 3 ручных вариантов; аналогично
объединяются другие «контекстно-зависимые» фичи.

## Этап 6 — Декларативные строковые литералы (замена hand-written терминалов)

Принцип (решение пользователя): декларативное описание правил предпочтительнее ручных
парсеров; hand-written матчеры — только там, где разбор невозможно или слишком сложно
выразить декларативно. Все литералы — декларативно, где возможно.

Контекст: после T3.5.2 интерполированные строки — грамматические правила (`Cs6.grammar`,
дыра = `{ Expression }`), но их текстовые/escape/format-части и ВСЕ не-интерполированные
строки (plain/verbatim/raw) остались hand-written терминалами (`CSharpTerminals.cs` +
`StringLiteralScanner.cs`). Причины: (1) в языке текстовых грамматик CsNitra НЕТ
char-классов (есть только литералы/ссылки/seq/alt/`*`/`+`/`?`/`&`/`!`/списки/TDOPP) —
«ран символов» не выразить; (2) движок пропускает trivia после КАЖДОГО терминала
(`Parser.cs:686-689`), а внутри строки whitespace/newline/комментарии — это КОНТЕНТ, не
trivia. Последствия (2): newlines «прозрачны» → 4 расхождения accept/reject с Roslyn
(CS1039/CS8997/CS9002/CS9000, дизайн §7.5); и побуквенный декларативный ран имел бы съеденные
trivia-сканером `//`/`/* */` внутри строки.

## Риски фреймворка (решаются точечно, когда упрёмся)

- Препроцессор `#if/#define/…` — отдельный текстовый проход до парсинга (как в Roslyn); маппинг позиций для диагностики.
- TypeChecker WIP (2 пропущенных теста) — диагностика текстов грамматики.
- Идентификаторы: в regex-движке нет combining-символов и `\u`-экранирований — при необходимости кастомный `Terminal`.
- Токены `?.`/`..` с допустимым whitespace между знаками — regex-терминалы вида `\?\s*[.[`.
- Ключевые слова vs идентификаторы — решено `WordLiteral` (T1.3.1.1): identifier-подобные литералы текста грамматики матчатся whole-word.
- Raw-строки с 4+ кавычками — hand-written `Terminal` (не-интерполированные) / контекстный парсер (интерполированные, Этап 4b).
